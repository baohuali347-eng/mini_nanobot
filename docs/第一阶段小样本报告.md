# 第一阶段真实模型小样本记录

2026 年 11 月 2 日，使用项目配置的 `deepseek-flash`，在内置 `clamp_and_slug` 任务上分别运行一次单 Agent、串行多 Agent、并行多 Agent。任务要求修复两个不同文件中的 clamp 和 slugify。

每种模式从同样的初始代码开始，独立工作目录；每次总预算 18 次模型调用和 HTTP 请求、150 秒。多 Agent 使用探索、两个实现、审查的固定 DAG。此次仅用于验证评测链路，样本不足以比较一般能力。

| 模式 | 最终代码外部验收 | 完整工作流 | Agent 耗时 | 模型调用 | 供应商 Token |
| --- | --- | --- | ---: | ---: | ---: |
| single | 通过 | 正常完成 | 13.67 秒 | 6 | 14,941 |
| serial | 通过 | 未正常完成：审查交接格式无效 | 50.46 秒 | 17 | 55,223 |
| parallel | 通过 | 未正常完成：审查阶段调用预算耗尽 | 25.57 秒 | 18 | 55,955 |

全部请求均返回了 `total_tokens`，用量覆盖率为 100%。Token 为供应商返回值之和，包含多轮重复输入，不等同于新增文本长度，也不等同于费用。

## 可以确认的结果

- 三种模式都实际修改了示例文件，并通过评测器保管的验收脚本。验收发生在所有角色停止后，使用新的解释器。
- 完成代码修复和完成协作流程是不同指标。本次只有单 Agent 同时满足“正常完成”和“外部验收通过”。
- 串行模式的探索与两个实现任务完成，审查阶段没有提交符合协议的交接，因此未算作工作流成功。
- 并行模式的两个实现任务完成，审查阶段触及共享调用上限，因此未算作工作流成功。
- 本次多 Agent 的调用和 Token 开销较高。两种协作流程均未正常完成，不能将两者的耗时比值当作完成相同工作的并行加速比。
