# 第三阶段：独立副本与补丁集成

本阶段让多个子任务在独立项目副本中工作，后端从真实文件变化采集补丁，组合验证后才发布到原目录。角色说“完成”不等于补丁已经发布。

## 当前执行链路

```text
原目录当前状态（包含未提交、未跟踪文件）
  ↓ 快照
探索：只读副本
  ├─ 实现 A：独立副本，只继承已完成前置的补丁
  └─ 实现 B：独立副本，只继承已完成前置的补丁
  ↓ 后端组合依赖补丁，执行可信验收
审查：只读组合副本，接收实际验收摘要
  ↓ 全部任务结束、合并全部补丁，再次验收
检查原目录未变化 → 写入发布日志 → 发布到原目录
```

独立任务不会看到兄弟任务正在修改的文件；有依赖的任务能读到前置产物。源码、输出格式、角色权限和模型调用仍复用现有 AgentRunner，等待依赖仍不占并发名额。

所有复制、补丁采集、集成、验收和发布均在 Python 后端。网页展示角色报告、补丁摘要和整体发布结果。

## 为什么使用副本

本项目可能面对没有 Git 的目录，也要保留用户大量未提交、未跟踪的工作。因此使用独立文件副本，不对原仓库执行 worktree、checkout、reset、clean、commit 或 git apply。

当工作目录本身有 `.git` 时，后端仅调用 `git ls-files` 读取文件清单，禁用 fsmonitor，不传递模型密钥。实际内容来自当前磁盘，不来自 HEAD 或索引。没有 Git 时使用受限目录遍历。副本使用独立文件，不以硬链接共享可写源码。

不复制 `.git`、`.env` 及 `.env.*`、依赖、构建和常见缓存目录；Git 项目还跳过被忽略的未跟踪文件。为了避免别名写入，代码清单中的符号链接会拒绝。默认最多 10000 个文件、单文件 5 MB、整体 100 MB，超过会停止，不截断后声称完整。

副本是并发修改隔离，不是进程安全沙箱。任意 Shell/Python 代码的系统权限仍需 Seatbelt/bwrap；配置沙箱后失败不会无隔离执行。

Shell 设置 Git 搜索上界，副本中的普通 Git 命令不会向上找到父仓库。选择的工作区自身有 `.git` 时仍正常使用；这只是防止无意越界，恶意脚本移除环境变量等行为仍需系统沙箱约束。实测发现与本地重放见 [第三阶段小样本报告](第三阶段小样本报告.md)。

## 计划中的文件归属

```json
{
  "action": "plan",
  "wait": true,
  "tasks": [
    {"id":"numbers","role":"coder","task":"修复数值工具","depends_on":[],"acceptance":["满足数值需求"],"write_paths":["numbers_util.py"]},
    {"id":"text","role":"coder","task":"修复文本工具","depends_on":[],"acceptance":["满足文本需求"],"write_paths":["text_util.py"]},
    {"id":"review","role":"reviewer","task":"审查组合后的代码与实际验收证据","depends_on":["numbers","text"],"acceptance":["独立报告审查发现"]}
  ]
}
```

`write_paths` 指项目内文件或目录前缀，不支持 glob；整批计划启动前检查路径边界。旧的 `create`/计划未指定时保留兼容范围 `["."]`，不会假装已经分配互不重叠的文件。新计划应始终明确归属。

不把依赖、构建或缓存排除目录中的文件作为子任务补丁交付；构建产物应在源码集成后由主任务生成。

文件写入工具在副本内立即拒绝超出范围的写入。Shell 的任意脚本无法只靠命令字符串限制到文件级，因此完成后再次从文件系统比较实际变化；越界修改不发布。补丁清单覆盖 Shell 产生的变化，与原有 `files_changed` 文件工具记录分别保存。

默认不允许子任务补丁删除原文件。确有需要时，在可信配置中显式设置 `"allowSubagentDeletes": true`；仍须在写入范围内并通过集成检查。模型不能通过完成报告开启删除权限。

## 冲突和验收门禁

- 独立分支修改同一文件而产生不同结果时，按文件粒度报冲突，不自动选择最后一个写入者。不做自动三方文本合并。
- 完全相同的改动可去重；前置 A 修改后，依赖 B 基于 A 继续修改同一文件可以顺序组合。
- 配置可信规则后，审查模型调用之前先执行组合验收；失败时不调用审查模型，原目录保持不变。
- 发布前对整个当前原目录与基线进行校对。即使用户修改的是补丁未触及的文件，也会保守阻断，避免在过期上下文上发布。
- 验收后再核对组合副本未变化。角色未完成、范围违规、冲突、验收失败或原目录变化，都会保留补丁并拒绝该批发布。

独立副本不包含 `.venv`、`node_modules`。隔离检查应使用已安装且可访问的解释器/工具；例如可信命令可使用 Python 解释器的绝对路径。原目录相对路径 `.venv/bin/python` 在副本内通常不存在；需要调整可信配置，不能失败后回到原目录执行同一检查并冒充候选验收。系统沙箱下的额外依赖读取也须显式配置只读授权。

普通聊天默认 `isolateSubagents=true`，可在可信配置中设 `false` 使用旧共享模式。没有验收规则时会标明 `not_configured`；发布成功只表示文件组合与版本检查通过，不代表自动验证了全部业务需求。

## 发布、取消和恢复边界

发布前保存日志，逐个文件进行同目录临时文件替换，保留权限。常规异常时，只回滚仍与本批写入结果一致的文件；若用户或其他进程又改了某文件，保留该修改，记录 `recovery_required`，不得覆盖它来伪装回滚成功。

多文件发布不是跨文件的系统事务。普通取消在同步发布段完成后才能处理；已经发布的批次不会因后续任务取消而自动撤销。进程强制结束或断电可能留下部分发布，须核对发布日志、基线、对象和当前文件；本阶段不自动重放或恢复未知操作。

任务停止后会清理命令进程组，并尝试归档已产生的合规部分补丁，不发布取消/失败任务。副本视图在请求关闭时删除，基线清单、文件对象、补丁、发布日志保留在数据目录的 `workspaces/run-*/` 下：

```text
workspaces/run-.../
├── baseline-0.json        # 初始当前工作区的版本和文件元数据
├── baseline-1.json        # 成功发布后的新基线（如有）
├── objects/              # 内容哈希寻址的文件内容，避免重复备份
├── numbers.json          # 实际补丁清单、前后哈希与权限
├── numbers.diff          # 便于阅读的差异；实际发布使用完整字节和模式
├── journal-0.json        # prepared / committed / rolled_back / recovery_required
└── outcome.json          # 最近一次集成结论（发生集成时）
```

记录目录权限 0700，JSON、diff 与对象默认 0600；可能包含用户代码，不应直接公开。归档会占磁盘，本阶段没有后台自动清理或工作区恢复执行器。会话的最新集成结论通过 SessionStore 的 SQLite 事务保存，刷新后不会依赖最近 100 条事件是否仍包含发布记录。

视图清理失败时会显示错误并保留目录，不阻塞会话结束；发布已提交但后续基线清单归档失败时保留“已发布”结论和警告，不伪装成未修改原目录。

验证范围内容哈希与发布全工作区哈希的范围/结构不同，不应直接比较。网页分别标注“验证时的产物版本”和“发布时的产物版本”，并把角色完成、验收通过、补丁发布分开显示。

## 评测入口

```bash
.venv/bin/python -m mini_nanobot eval --case clamp_and_slug \
  --isolate --repairs 2 --report-repairs 1 \
  --max-calls 30 --timeout 180 --output eval_results/stage3_smoke
```

评测默认开启隔离，`--shared-workspace` 保留共享模式用于对照。单 Agent 本来就在该次独立试验目录内工作；隔离开关改变多 Agent 子任务的执行方式。

结果记录 `isolated_subagents`、集成状态和冲突数量。`integration_conflicts` 包含文件重叠、归属违规、禁止删除和基线变化；`overlap_conflicts` 单独统计不同独立补丁修改同一文件。未发布候选的代码不冒充最终工作区验收成功。

所有角色、格式更正、业务修复共享原调用预算，全部轮次合计最多 12 个子任务。本阶段也收敛了角色提示中的重复读取、重复验证和清理缓存行为；比较真实模型时应同时记录预算和引擎哈希，不把单次改善完全归因于隔离机制。
