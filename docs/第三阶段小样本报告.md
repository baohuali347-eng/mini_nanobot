# 第三阶段真实模型小样本与边界修复

2026 年 11 月 2 日，使用 `deepseek-flash`，在内置 `clamp_and_slug` 合成任务上分别运行单 Agent、串行多 Agent、并行多 Agent 各一次。多 Agent 开启独立副本、真实补丁、组合验收与发布；每次总上限为 30 次模型 / HTTP 请求、180 秒，全部角色与修复共享额度。

| --- | --- | --- | ---: | ---: | ---: |

| parallel | 补丁已集成并发布 | 通过 | 46.98 秒 | 17 | 59,301 |

全部请求均返回 Token 用量，覆盖率 100%。执行器耗时包含副本、图内组合检查与发布，扣除外层逐轮验收；最终外部复核另记。两种多 Agent 发布日志均为 `committed`，集成验收为 `passed`，没有冲突，业务修复次数为零。

格式更正按每项交接限次：串行审查发生一次，并行的探索和审查各发生一次，均计入总调用和 Token；没有因更正重置预算或执行更正响应中的工具。

这是一个任务、每模式一次的链路验证，不是 16 项任务的全量实测。相比之前的 18 次请求预算，本次上限提高到 30，角色提示也收敛了重复读取、验证与缓存清理行为，不能把不同阶段的变化全部归因于隔离机制。

本次单 Agent 明显更快；串行和并行耗时接近。结果支持“隔离、交接、组合验证与发布链路可完成”，不支持“多 Agent 普遍更快”的结论。较小任务的角色与交接开销仍然明显。

## 核对发现的 Git 搜索边界

实测结束后核对原始工具记录，发现串行实现角色的一条组合验证命令末尾执行了 `git status --porcelain`。副本没有 `.git`，但位于另一个仓库的子目录内，Git 向上找到了父仓库，产生了该仓库的文件名与状态列表。这些元信息随工具结果进入了后续模型请求，超出了本次合成示例应包含的范围。

该 Git 子命令是状态查询，没有执行 add、commit、reset、checkout 等操作；日志里也没有读取父仓库源文件正文的命令。全部本地评测记录核对未发现配置的模型密钥。原始日志仍包含父仓库文件名和状态，不应直接公开。

此边界此前遗漏，现已在 Shell 的受限子进程环境中设置 `GIT_CEILING_DIRECTORIES`，让常规 Git 命令停止在所选工作区边界；工作区本身有 `.git` 时仍可正常访问自己的仓库。它防止无意发现父仓库，不替代 Seatbelt/bwrap 对恶意脚本的进程隔离。

随后只做了本地验证，没有追加模型调用：

- 对实测中的同一条命令，在父仓库下的新副本中重放。
- 输出仅有合成代码的 TypeError、幂等性和导入验证结果，不再出现父仓库状态列表。
- 重放前后的原仓库索引字节一致，模型调用数为零。
- 新增回归验证副本无法发现父仓库，选择仓库根目录时 Git 查询仍正常。

三次原始评测保留修复前的引擎哈希与成绩，没有修改为“修复后重新实测”。本地重放证据位于 [stage3_git_boundary_replay.json](../eval_results/stage3_git_boundary_replay.json)。
