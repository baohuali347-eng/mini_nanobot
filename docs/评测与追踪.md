# 第一阶段：评测基线与调用追踪

这一阶段提供固定代码任务、可重复执行的三种策略、外部验收以及可核对的原始事件。它用于回答：多 Agent 是否提高任务成功率、并发是否减少耗时、增加了多少模型调用和 Token。

默认评测三种**固定工作流**。新增可选的 `auto` 模式，用主模型自行决定直接执行或委派子任务，观察自主选择带来的完成率、耗时和调用开销。第二阶段已支持可选的验收失败修复与格式更正，见 [验收与有限修复](验收与有限修复.md)；第三阶段已加入 [独立副本与补丁集成](隔离与补丁集成.md)，评测默认开启，可用 `--shared-workspace` 对照。

## 先离线检查任务集

```bash
.venv/bin/python -m mini_nanobot eval --list
.venv/bin/python -m mini_nanobot eval --self-check --output eval_results/self_check
```

自检不读取默认模型配置、不调用外部模型。它在两个全新目录分别放入初始代码与参考实现，要求初始代码不能通过验收、参考实现必须通过。输出目录必须不存在；不会覆盖旧结果。

内置 16 项合成 Python 任务，全部仅依赖标准库：

| 类别 | 数量 | 任务 |
| --- | ---: | --- |
| 单文件修复 | 4 | 四则运算、中位数、分页、slug |
| 跨文件修复 | 4 | 折扣发票、布尔配置、库存、运费结算 |
| 独立模块修改 | 4 | clamp 与 slug、闰年与温度、去重与二分搜索、时长与分块 |
| 共享接口修改 | 4 | 整数分金额、字符串用户 ID、面积 property、结构化解析结果 |

这是小型诊断任务集，尚未覆盖大型仓库、复杂依赖或真实开源 issue。任务和参考实现一起存放在 `mini_nanobot/eval_cases.json`，不能将它当作防数据污染的盲测基准。

## 真实模型小样本

使用正常 `.env` / `config.json` 中的模型配置。真实评测会发送任务提示、合成代码和工具反馈并产生模型费用；不会复制用户项目到任务目录。

```bash
.venv/bin/python -m mini_nanobot eval \
  --case clamp_and_slug \
  --mode single --mode serial --mode parallel \
  --max-calls 18 --timeout 150 \
  --output eval_results/smoke
```

每次试验都会创建新的工作目录、SQLite 数据目录、独立模型客户端；不同模式和重复次数不会共用已修改的代码、记忆或会话。各次试验顺序执行；`parallel` 指一次试验内实现角色的并行。

五种模式如下，省略 `--mode` 时仍运行前三种：

| 模式 | 工作流 |
| --- | --- |
| `single` | 一个可读写的 Agent，直接完成需求，没有委派工具 |
| `serial` | 探索 → 实现 A → 实现 B（如有）→ 审查 |
| `parallel` | 探索 → 所有实现任务并行 → 审查 |
| `auto` | 主模型先探索，自行直接完成、创建子任务或提交依赖计划 |
| `auto_legacy` | 相同引擎和工具权限下，重放优化前的委派系统提示及工具说明 |

串行、并行使用相同的任务拆分、角色提示和验收要求，仅改变实现任务的依赖边和并发名额。两种模式均复用 `SubagentManager` 和 `AgentRunner`；探索、审查保持只读工具权限。编排由评测器固定，不额外增加一个模型规划者。

`auto` 给主模型与日常使用相同的普通工具和 `subagent` 工具，复用依赖调度、独立副本、工具反馈及最终结果等待。评测器不注入固定计划。主模型最终仍按评测协议提交完成声明，之后执行独立验收；该声明和子任务自报都不能替代测试通过。主模型探索、规划、格式更正和全部子任务共享同一个请求与时间预算。

`auto_legacy` 同时替换委派系统段落和 `subagent` 工具说明，其他系统指令、执行器、模型、预算和任务与 `auto` 一致。这是旧委派提示在当前引擎上的对照，不是还原整个历史版本。默认网页和 CLI 编程始终使用当前提示。每轮结果中的 `delegation_prompts.json` 保存两版完整委派提示，`delegation_prompt_hashes` 保存其哈希，以便后续改动后核对。

选择提示词默认鼓励主模型直接完成定位明确、修改量小或紧密耦合的任务。探索后能明确目标、文件归属、交接信息、验收要求，且工作量值得协作开销时才委派。可只增加一个审查角色，用户明确指定模式时遵循其要求。这些是模型选择的提示依据，尚未构成经实测证明最优的路由规则。

可以先比较单文件和双文件任务，每种重复两次，真实调用会产生模型费用：

```bash
.venv/bin/python -m mini_nanobot eval \
  --case arithmetic --case clamp_and_slug \
  --mode single --mode auto --repeat 2 \
  --max-calls 18 --timeout 90 --report-repairs 1 \
  --output eval_results/auto_choice
```

同一任务即使 `auto` 最终选择单 Agent，也会产生提供委派工具和自主决策的开销。逐次报告记录 `subtasks_created` 和 `subagent_tool_calls`，按模式摘要给出 `delegation_rate` 和 `mean_subtasks`。前者表示创建过子任务的试验比例，后者是平均创建数，取消和前置阻断的任务也计入创建数。`subagent_tool_calls` 包含 plan、create、check 等操作及参数无效的尝试，不能将它直接解释为成功委派次数。子任务 ID 按业务修复轮次区分。

比较时先核对完整成功率，再比较耗时与 Token。不能把“少委派”自动当作选择正确，也不能用两个小任务证明大型任务应当使用单 Agent。调整提示词后应使用新的结果目录，保留全部失败，并用额外任务和重复运行检查是否只适应了已知样例。

### 业务规则与委派提示对照

补充任务在 `mini_nanobot/eval_suites/routing_checks.json` 中单独保存，不改变原 16 项任务。`audit_and_calendar` 包含可独立修改的审计汇总、预约空档模块，覆盖带时区时间窗口、重叠区间、跨日、统计及非法输入。`invoice_pipeline` 包含相互依赖的金额解析、逐行折扣、发票汇总接口，覆盖 Decimal 舍入、输入类型和空列表。这些是业务规则更密集的合成任务，仍未覆盖大型真实仓库。

题目、初始实现、参考实现和外部验收在真实调用前固定，离线自检要求缺陷实现失败、参考实现通过。任务集文件哈希在 `eval_results/routing_checks_20261105_frozen.json` 中冻结。本轮使用 2 题 × 4 模式 × 1 次重复，共 8 次试验，保持每次 18 次请求、90 秒、0 次业务修复和最多 1 次格式更正的上限。模式包括 `single`、`parallel`、`auto`、`auto_legacy`，通过同一轮随机顺序比较委派选择与固定策略。

```bash
.venv/bin/python -m mini_nanobot eval \
  --suite mini_nanobot/eval_suites/routing_checks.json \
  --mode single --mode parallel --mode auto --mode auto_legacy \
  --repeat 1 --max-calls 18 --timeout 90 --report-repairs 1 \
  --output eval_results/routing_checks_comparison
```

任务和验收由同一协作助手设计，没有独立外部标注。每题每模式只有一次运行，结果用于定位选择与协作失败，后续仍需额外任务和重复测量。题目描述提供文件范围和各项需求，但不指示必须使用哪一种模式。

本轮 8 次真实运行已全部结束。正常完成同时要求工作流结束和独立验收通过，预算耗尽、超时不会因最终代码通过验收而改记成功。

| 模式 | 正常完成并通过验收 | 最终代码通过验收 | 平均秒数 | 子任务数 |
| --- | ---: | ---: | ---: | --- |
| single | 1/2 | 2/2 | 70.04 | 两题均为 0 |
| parallel | 0/2 | 0/2 | 45.83 | 审计题 4，发票题 3 |
| auto | 0/2 | 1/2 | 57.03 | 两题均为 0 |
| auto_legacy | 0/2 | 1/2 | 49.56 | 两题均为 0 |

审计题中，single 和 auto_legacy 耗尽 18 次调用，auto 达到 90 秒超时，三者最终代码均通过独立验收。工具轨迹显示模型自写断言存在不符合题意的预期，随后多次调整自测；旧提示试验还追加了验证与缓存清理。固定并行在共享预算耗尽时未完成交接和发布，原目录验收失败。

发票题的 single 正常完成。auto、auto_legacy 和固定并行均出现 HTTP 400。两种自主模式出错前的一次响应均为 `finish_reason=length`，仅含思考字段、没有正文或工具调用，执行器随后发起续接。旧版适配器未保留服务端错误正文，无法从这些记录确定 HTTP 400 的完整原因，因此不能把该故障归因于委派提示本身。

本轮合计 96 次 HTTP 请求，均在逐次上限内。已知供应商 Token 合计 1,022,709，部分失败或取消请求缺少用量回包，完整总用量未知。全部结果位于 `eval_results/routing_checks_20261105_comparison/`，包含逐次追踪、两版提示快照、完整运行源码 `engine_snapshot.json`。源码指纹为 `82d8fe60124e511c7cd4f5260a2518c48332d503ef170079b7c78549b5326486`，任务集 SHA-256 为 `47529b31f8ad1643fdde5913840ecef20c47dcdf397f9b156b38d4513d285af1`，与调用前冻结记录一致。

结果表明，在当前调用和时间预算下，新增业务任务的工作流可靠性不足，两版自主选择均未委派子任务，也没有显示新提示的收益。每题仅运行一次，不能据此判定大型任务的最优协作方式，也不能把提前报错后的较短耗时视为效率优势。

### 根据本轮失败修复执行与收尾

完成上述 8 次运行并冻结源码后，增加了以下处理，原成绩保持原样。

- 委派策略补充自写断言核对与验证后的收尾要求，避免围绕错误预期反复修改或为收尾重复验证。
- 单次 `max_tokens` 由硬编码 4096 改为读取 `maxOutputTokens` 配置，默认仍为 4096，结果 manifest 记录实际值。
- 纯思考输出在长度上限截断、未返回正文或工具调用时明确停止，不继续提交该不完整响应。旧会话恢复时跳过没有正文和工具调用的空助手消息，保留此前配对的工具结果。
- 服务返回 `reasoning_content` 字符串时保留该字段，包括空字符串。HTTP 错误显示脱敏、限长的服务端说明，便于区分协议与业务失败。

DeepSeek 文档要求工具调用请求回传此前的思考字段。适配器据此保留服务实际返回的字段，相关行为由协议替身回归验证。[官方思考模式说明](https://api-docs.deepseek.com/guides/thinking_mode/)

这些后续修改只做离线回归，没有追加真实模型试验。第二轮的结果反映修复前版本，修复后是否提升真实成功率需要在新的结果目录单独验证。

结果位于 `eval_results/routing_checks_20261105_repaired/`，实测源码保存在 `engine_snapshot.json`，引擎哈希为 `94f358dfe2741cb17ee4227676a9e3f62575f9b23c5d4b5193fb925ea5c0c5dd`。调用前的完整源码与任务哈希另存于 `eval_results/routing_checks_20261105_repaired_preflight/frozen.json`。本轮题集 SHA-256 与前轮冻结值一致。

实测结束后，最终版本将默认单次输出上限统一为本轮使用的 8192，并向模型显示当前共享请求剩余额度，提醒为汇报保留请求。截断保护扩展到带工具调用的响应，避免部分工具执行。上述最后收口改动通过离线回归，合计 131 项测试通过，ruff 与架构边界检查通过；没有再次调用付费模型。最终版本的记录保存在本轮结果目录中的 `finalization.json`，与实测版本分开标记。

日常使用仍先由主 Agent 探索并直接处理，只有明确分工及协作收益时才委派。当前实现的自主委派属于模型选择策略，本轮实测支持两个业务任务的直接修复链路，尚不支持“已找到最优单多 Agent 路由”或“多 Agent 更快”的表述。

单文件、跨文件任务目前只有一个实现角色，没有实现阶段的并发收益。独立模块、共享接口任务各有两个实现角色，可用来观察并发收益和接口协作成本。共享接口任务中，单个角色验证时可能看到另一项尚未完成的接口，属于当前共享目录设计需要观察的行为。

## 扩大样本与复现

完成小样本后，可自行运行全部任务并重复三次：

```bash
.venv/bin/python -m mini_nanobot eval \
  --repeat 3 --max-calls 30 --timeout 180 --seed 42 \
  --output eval_results/baseline
```

全部 16 项 × 3 种模式 × 3 次重复，共 144 次试验。应先按小样本的实际用量评估费用。`--seed` 只控制试验顺序，不保证远端模型输出确定；默认不在验收失败后自动重跑；启用 `--repairs` 后按限次策略继续当前代码的修复。

每次试验的调用预算由全部角色和上下文摘要共享：

- `--max-calls` 同时限制逻辑模型调用次数和实际 HTTP 请求次数，HTTP 重试也消耗请求额度。
- `--timeout` 限制所有角色与中间验收的总时间；超时会取消子任务，执行中的命令沿用进程组清理。
- 外部验收单独最多 15 秒，其耗时不计入 Agent 执行耗时。
- 模型、上下文预算、单角色轮次上限一致。串行模式并发为 1；并行模式使用配置中的子任务并发上限。

如果要对比模型或提示词版本，应保留旧结果，在新目录运行，核对 `manifest.json` 中模型名称、接口地址、引擎源码哈希、任务哈希、预算及调度种子。接口返回的模型别名可能随服务商更新，记录名称不等于锁定了不可变的模型版本。

可用 `--case` 重复选择任务，用 `--mode` 重复选择模式。任务集文件可通过 `--suite` 指定，但其中的 Python 验收代码将被执行，只能使用可信任务集。

## 验收与指标

全部 Agent 停止后，评测器在新的 Python 解释器中执行自己保管的验收脚本；模型的完成声明与外部验收结果分别记录。脚本不会作为工作区文件交给 Agent，模型自己新增或修改测试文件不能替代外部验收。验收进程使用 `-I`、受限环境变量、命令超时及已配置的沙箱；不会继承模型密钥。

| 指标 | 定义 |
| --- | --- |
| 成功率 | 正常完成且最终外部验收通过 / 全部试验 |
| 首轮成功率 | 首次执行正常完成且首轮验收通过 / 全部试验 |
| 验收通过率 | 最终外部验收通过 / 全部试验，不要求角色自报完成 |
| 错误完成率 | 自报完成但外部验收失败 / 自报完成次数；无声明时为未知 |
| 执行耗时 | 角色开始到全部角色清理完毕；不含外部验收 |
| 模型调用次数 | 包含所有角色和摘要的逻辑调用 |
| HTTP 请求次数 | 包含供应商请求重试 |
| Token | 供应商返回的每次 HTTP 请求用量之和 |
| 用量覆盖率 | 获得 `total_tokens` 的 HTTP 请求数 / 实际请求数 |

错误、超时、预算耗尽都保留并计入分母，不只统计成功案例。首轮执行允许模型根据正常工具反馈修改代码；默认基线没有外层修复，因此成功率与首轮成功率一致；启用 `--repairs` 后分别记录最终与首轮成功率。

有任何请求缺少 Token 用量时，整次试验的 `total_tokens` 为 `null`，报告显示“未知”；`known_total_tokens` 只表示已知部分。失败或中断的请求可能已消耗 Token 但没有用量回包，不能按零计费。未设置价格表，不估算费用。

`streamUsage` 默认 `true`，请求带上 `stream_options.include_usage`。若兼容接口拒绝该选项，可在配置 JSON 中显式设置 `"streamUsage": false`；不会因收到错误而隐式更改协议重发请求。没有用量仍可比较验收和耗时。

普通聊天也会将新增 `model` 事件通过 SessionStore 事务保存，网页继续处理原有文本、工具和任务事件。`GET /api/sessions/{id}` 仍只返回最近 100 条活动；评测的 JSONL 保留该次完整追踪。

模型事件记录 `run_id`、`session_id`、`task_id`、`parent_task_id`、`role`、`span_id`、`parent_span_id`、`request_id`、`attempt`、`purpose`、UTC 时间、耗时及用量。每次逻辑调用有一个 span，每次 HTTP 重试有独立 request ID。工具 span 指向产生它的模型 span，子任务模型 span 可指向创建它的工具 span。`purpose=compaction` 可识别摘要开销，`purpose=report_repair` 标识格式更正；`workflow_attempt` 区分业务修复轮次。

模型事件不保存 Authorization 或完整请求体；文本和工具事件仍会包含回复、代码片段、命令输出。结果默认放入已忽略的 `eval_results/`，目录权限 0700、JSON/JSONL 权限 0600；分享前仍应检查内容。报告中的绝对路径不应直接作为公开作品展示。

## 当前边界

- 不同试验之间使用独立工作区；多 Agent 默认使用独立副本并检测补丁冲突，`--shared-workspace` 才采用原共享模式。
- 文件工具立即执行归属检查，Shell 的越界写入通过实际差异阻断发布；任意脚本的系统权限仍需 Seatbelt/bwrap。
- 验收面向非对抗的代码修复任务，不宣称能够抵抗恶意代码对解释器、验收流程或外部文件的攻击。
- 保存真实补丁和文件哈希，记录集成冲突与文件重叠冲突；采用文件级冲突检测，不进行 Git 三方自动合并。
- 不恢复中断试验、不自动重试未知工具操作。已结束试验的结果及实时刷新的追踪会保留。
- 小样本报告验证评测入口与数据口径，不能证明多 Agent 对一般编程任务更优。
