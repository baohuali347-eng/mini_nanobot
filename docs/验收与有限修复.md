# 第二阶段：可信验收与有限修复

本阶段把“模型汇报完成”和“后端实际验收”分开。普通聊天可以配置可信命令，评测可以启用验收失败后的有限修复；交接格式无效时允许单独整理 JSON。所有模型调用、HTTP 重试、摘要和修复共享同一预算。

## 普通聊天如何启用

在启动时读取的配置 JSON 中加入以下字段，保留原有模型连接与其他配置。例如给本仓库配置：

```json
{
  "maxModelCalls": 60,
  "runTimeout": 600,
  "validation": {
    "maxRepairAttempts": 2,
    "reportRepairAttempts": 1,
    "commands": [
      {
        "id": "python_tests",
        "command": ".venv/bin/python -m pytest -q",
        "paths": ["mini_nanobot", "tests", "pyproject.toml"],
        "workingDir": ".",
        "timeout": 120
      }
    ]
  }
}
```

这段示例是需要合入现有配置的片段，不会由程序自动写入。也可用 `web --config 文件` 或 `code --config 文件` 指定完整配置；重启后生效。不要向命令中填入密钥。

命令来自启动时的可信配置，不从 AGENTS.md、项目内可编辑文件或模型输出中自动加载。只配置可重复运行的检查，不将部署、推送等操作作为验收命令。默认没有验收命令，页面会显示“未配置后端验收”，不会将普通角色汇报显示成机器验收。

`paths` 是本次验收结论对应的产物范围，支持项目内文件或目录，默认 `["."]`；不支持 glob。请覆盖相关源码、测试、依赖声明和测试配置。过窄的范围会漏掉相关变化，默认全目录又可能包含会变化的报告文件，实际使用应明确配置。

源码范围不自动阻止模型改动测试。用户项目的测试仍需要审查其质量与修改；命令退出码为零只说明配置的检查执行通过，不证明所有自然语言需求均已满足。内置评测的验收脚本由评测器保管，不放入候选工作区。

## 正常执行和修复

```text
模型完成当前工作 → 回收全部子任务 → 后端执行可信验收
    ├─ 通过：保存产物哈希与实际结果
    ├─ 失败 / 产物变化：反馈失败资料，启动新的执行轮次
    └─ 配置或权限错误：停止，不自动更换命令或关闭沙箱
```

默认最多两次业务修复，即首次执行加最多两次修复。每次修复继续使用当前文件，不回滚、不盲目重放旧工具调用；由模型先检查当前结果再决定操作。失败输出仅作为资料，不能覆盖用户需求；原始请求为只读时不允许为了通过验收擅自改代码。

每个执行轮次中的 DAG 仍必须无环。新轮次使用新的子任务管理器，ID 在该轮次内唯一；`workflow_attempt` 区分不同轮次。每次请求全部轮次合计仍最多 12 个子任务，取消和阻断也不退还名额。

`maxModelCalls` 同时约束逻辑调用和真实 HTTP 请求数量，重试也消耗额度。`runTimeout` 覆盖普通聊天的全部执行、验收和修复。到达上限会停止；超时和用户取消继续清理命令进程组与子任务，不会自动无隔离重跑。

业务修复耗尽后会话状态为 `needs_followup`；模型或预算异常为 `error`，用户停止为 `cancelled`。验收处于等待时中断，会保存为 `not_run`，不会继承上一轮的通过结论。所有规则通过后会话才正常结束；语义审查仍由模型和用户承担。

## 子任务的验收门禁

模型只能在实现任务中引用已配置的 ID：

```json
{
  "id": "implement",
  "role": "coder",
  "task": "修复指定模块并验证",
  "depends_on": ["explore"],
  "acceptance": ["满足需求并保持接口兼容"],
  "validation": ["python_tests"]
}
```

未知 ID、非实现角色引用验收、越界路径等在登记整批计划前拒绝，不启动部分节点。模型不能通过计划字段添加验收命令。

有验收 ID 的任务先提交角色报告，再进入 `validating`；实际检查失败则进入 `needs_followup`，即使模型自报 `completed` 也不会放行依赖任务。没有配置验收 ID 的任务保留原角色完成语义，交接中明确为 `validation.status=not_configured`，不是自动验收。

共享目录中应给每个子任务选择对应源码范围的独立检查；对整个项目的集成检查放到最终验收。全量检查可能在另一个实现任务尚未结束时失败。共享模式没有修改隔离；第三阶段已支持 [独立副本与补丁集成](隔离与补丁集成.md)，但中间任务仍应使用对应范围的检查。

## 验收结论绑定版本

验收前后对 `paths` 中的完整文件集合计算 SHA-256，包括新增、删除和文件内容变化。命令成功但前后产物不一致时标记 `stale`，不能当作通过。依赖目录、Git 内部目录、缓存和环境密钥文件不纳入默认目录扫描；显式引用 `.env` 或越界符号链接会拒绝。

结论记录：

- `status`：`passed`、`failed`、`stale`、`error`、`cancelled`、`not_run` 或 `not_configured`。
- `artifact_hash` / `artifacts`：验收前的完整产物摘要及各文件哈希。
- `policy_hash`：实际规则 ID、命令、路径、目录与超时的哈希。
- `checks`：后端记录的真实退出码、超时和输出，独立于角色的命令工具记录。
- `attempt`：对应的业务执行轮次。

读取会话快照时重新核对已通过结论的产物与规则，变化则显示“验收结果已过期”；旧退出码保留为历史证据。本次请求运行期间，读取已通过的子任务交接或启动其下游时也核对版本，过期会阻断下游。会话增加一个 JSON 验收列，通过 SessionStore 的事务增量迁移，保留所有旧消息、事件和记忆。

快照核对不是持续文件监控，也不是并发写入隔离；前后哈希不能排除执行期间发生后又还原的瞬时修改。此阶段针对协作中的非对抗性错误，不宣称防止恶意程序篡改解释器或检查流程。

## 交接格式更正

任务首次执行后，若最终回复为空，或 `outcome`、`summary`、`unresolved` 不符合协议，普通聊天默认允许一次额外模型调用整理格式。空回复仅在没有待执行工具的最终答复位置处理；更正保留原事实与未解决问题，不要求重做任务。

格式更正请求不提供工具，后端也拒绝响应中的任何工具调用，不执行其中的写文件或命令。`purpose=report_repair` 可单独统计其模型开销。更正次数耗尽仍为错误，不能以宽松解析或删去未解决问题来伪造通过。

## 在同一任务集上对比

评测的默认参数保持基线行为：`--repairs 0 --report-repairs 0`。第二阶段显式开启：

```bash
.venv/bin/python -m mini_nanobot eval \
  --case clamp_and_slug \
  --repairs 2 --report-repairs 1 \
  --max-calls 18 --timeout 150 \
  --output eval_results/stage2_smoke
```

同一试验全部轮次共享 18 次调用，不会每次修复重新获得额度。每轮重建同一种固定 DAG，携带失败反馈，保持现有角色权限。超时预算覆盖执行与中间验收；所有角色退出后还会进行一次最多 15 秒的最终外部复核，不再调用模型。

报告区分最终成功率与首轮成功率，保留每轮报告状态、验证结果和 `repairs_used`。格式更正不算业务修复，但计入总调用和 Token。执行耗时扣除中间验收，完整验收耗时保存在逐轮记录中。旧阶段的真实样本保留原始引擎哈希；不同版本和单次随机输出的比较只用于诊断。

`attempt` 在模型事件中继续表示 HTTP 尝试次数；`workflow_attempt` 表示业务执行轮次，避免 HTTP 重试与业务修复混淆。网页按轮次区分同名子任务，独立展示角色汇报和后端验收结果。
